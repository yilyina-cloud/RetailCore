# Architecture canvas — RetailCore AS-IS

Описание основано на кейсе, исходной схеме, пяти интервью и фрагменте OrderProcessingService.java.

| Раздел | Описание |
| --- | --- |
| Ценность для бизнеса | Платформа обеспечивает оформление и выполнение заказов. Бизнесу нужны стабильная работа, более быстрые изменения и достоверные данные. Через три месяца требуется разобраться в текущем состоянии, через год — запустить новые сервисы. |
| Стейкхолдеры | Бизнес-заказчик, команды заказов, логистики, платежей, поддержки, аналитики, инфраструктуры и эксплуатации. Внешние участники — клиенты, маркетплейсы, платёжные провайдеры и службы доставки. |
| Основные функции | Расчёт цены и промо, оформление заказа, проверка наличия и резервирование, создание платёжной сессии, выбор доставки, управление статусами, обработка исключений и отчётность. |
| Требования к качеству | Устойчивость оформления, оплаты и доставки; работа в сезонные пики; понятная история заказа; согласованность данных; возможность внедрять изменения поэтапно. SLA/SLO, RTO/RPO, RPS/TPS, p95/p99 и допустимые задержки не определены. |
| Бизнес-контекст | Заказы поступают с сайта, из приложения и маркетплейсов. Платформа взаимодействует со складами, платёжными провайдерами и службами доставки. Поддержка разбирает обращения, бизнес использует отчёты. Правила обработки различаются по каналам, регионам и партнёрам. |
| Основные компоненты | Java-монолит управляет основным процессом заказа. Oracle хранит данные, часть правил и таблицы обмена. Вокруг работают .NET-сервис интеграций, Python-задания аналитики, инструменты поддержки, очереди и пакетные задания. |
| Ключевые решения текущей архитектуры | Основная обработка сосредоточена в монолите. Oracle используется одновременно как БД, место выполнения бизнес-логики и способ обмена между компонентами. Правила распределены между кодом, БД и настройками. Используются синхронные вызовы, очереди, таблицы и выгрузки. |
| Технологии | Java, Oracle, Python, .NET. Собственный дата-центр, физические серверы и ограниченная виртуализация. REST, очереди, обмен через таблицы, задания по расписанию и CSV. Конкретный брокер в материалах не указан. |
| Риски и недостающие данные | Скрытые зависимости мешают изменениям. Статусы и правила отличаются между компонентами, повторы могут создавать дубли. Аналитика нагружает операционную Oracle. Часть обработки и диагностики зависит от людей. Не хватает полной карты зависимостей, границ транзакций, измерений нагрузки, правил деградации и восстановления. |

## Основные ограничения

- Нельзя остановить бизнес ради полной миграции или заморозить выпуск новых функций на год.
- Серверные ресурсы близки к пределу; расширение требует закупок и согласований.
- В Oracle накоплены десятки терабайт данных, архивирование выполнено частично.
- Отказ от Oracle и других зарубежных компонентов должен быть постепенным.
